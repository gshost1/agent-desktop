### SURFACE-1: Closed-direction menu wait has no "not yet opened" state (Linux encodes it as a bool + a 2 s file timestamp)

- Pieces
  - Core passes only a bool: `crates/core/src/commands/wait.rs:109-133` (`adapter.wait_for_menu(process, open, deadline)`), trait `crates/core/src/adapter/system.rs:304-311`, mode `crates/core/src/commands/wait_mode.rs:45-56`.
  - Linux: `crates/linux/src/system/menu/menu_wait.rs:126-160` (`state_never_read`, `seen_open`, `recent_action()`); clock `crates/linux/src/system/interaction/action_clock.rs:5,21-31` (`WINDOW_MS = 2_000`); persisted store `action_clock_store.rs` (file per pid under `$XDG_RUNTIME_DIR/agent-desktop-actions`, boot-ms + instance token, `KEEP_MS 60_000`); markers only at `crates/linux/src/adapter.rs:288` (ref actions) and `crates/linux/src/system/adapter.rs:131,143` (press_key_for_app/window).
  - macOS: `crates/macos/src/system/wait.rs:12-29` (first read equal to `open` returns).
  - Windows: `crates/windows/src/system/wait.rs:60-84` (first read equal to `open` returns; only `state_never_read`).
  - Contrast (correct shape that already exists): `wait --event surface-dismissed` diffs against a grow-only `seen` set (`crates/core/src/commands/wait_event.rs:98-124`, `wait/signals.rs:211-223`) and batch pre-captures its baseline before the previous entry (`src/batch/execution.rs:61-62,177-185`, only for `wait --event`).
- States today
  ```
  core: open:bool ──► adapter
  Linux:   Polling{seen_open:bool, never_read:bool} + external file clock(pid) ──closed && (seen_open || clock>2s)──► Ok
  macOS:   Polling ──first read == open──► Ok
  Windows: Polling{never_read} ──first read == open──► Ok
  ```
  The real lifecycle is `NotYetOpen -> Open -> Closed`, plus `Unreadable`. Only Linux distinguishes NotYetOpen, and only through a heuristic.
- Illegal / unhandled transitions
  1. **macOS and Windows: `NotYetOpen` read as `Closed`.** `click <opener>` then `wait --menu-closed --app X` (two CLI calls, or one batch): first poll at t≈0 reads no menu, returns `{"found":true}`. The doc `docs/solutions/runtime-errors/a-wait-for-closed-right-after-the-opener-is-satisfied-falsely.md` documents exactly this for GTK4 (157-688 ms open latency) and says "do not size the hold from one toolkit", but the fix lives only in the Linux adapter. Code CONFIRMED (traced: `wait.rs:123` → `macos/system/wait.rs:15` / `windows/system/wait.rs:69`); timing on macOS/Windows SUSPECTED (needs a probe: Win32 popup after SendInput, Chromium DOM menu, macOS right-click CGEvent).
     Test sketch (FAILS on main): core `wait_scenario_menu_tests.rs` style stub adapter is not enough because the logic is in adapters; for Windows add a `forced_menu_states` seam next to `poll_calls` in `crates/windows/src/system/wait.rs` returning `[false, false, true, false]` after a recorded action, assert `wait_for_menu(open=false)` makes ≥4 polls. Equivalent for macOS via an injectable `is_menu_open`. With the proposed core loop (below) this becomes a pure core test with a stub `menu_state` adapter.
  2. **Linux: raw input never marks the clock.** `mouse-click --xy X,Y --button right` (→ `LinuxAdapter::mouse_event`, `crates/linux/src/adapter.rs:337-343`) and `drag` (`:345-351`) do not call `mark_outcome`, so `wait --menu-closed --app X` right after a coordinate right-click returns on the first closed read. CONFIRMED (traced; no pid is known for raw input, so the current design cannot mark it).
     Test sketch: `menu_wait_tests.rs` `FakeWorld::new(vec![Ok(false), Ok(true), Ok(false)])` with `recent` false (which is what a raw click produces today) → `run(open=false)` returns after 1 read; assert it should hold.
  3. **Linux: opener slower than 2 s** (busy app, first popover of a cold GTK4 app) → `recent_action()` turns false before the menu shows → false closed. SUSPECTED (needs probe on a loaded machine).
  4. **Open direction has no baseline either:** a menu left open from earlier satisfies `wait --menu` at once on all platforms. CONFIRMED by code (`menu_wait.rs:136` `open ||`), impact low.
- Hidden cost (estimate): Linux holds `wait --menu-closed` up to 2 000 ms after *any* started action to that pid, including the common "click a menu item, then wait --menu-closed" where the menu is already gone: `seen_open=false`, `recent=true` → polls (50 ms each, full registry + window walk) until 2 s after the click. ~1.5-2 s per such wait, ~30-40 wasted AT-SPI scans. CONFIRMED by code (`menu_wait.rs:136`), not measured.
- Impact: **B** (false success of a wait; downstream it can become A when the next action lands while the menu opens).
- Proposed explicit form: core-owned loop. Adapter exposes `menu_state(process, deadline) -> MenuReading { Open, Closed, Unreadable }` (Linux already has it: `menu_open` + `settle`). Core `MenuWaitPhase { AwaitingOpen { hold_until: Instant }, SeenOpen, Done }` with one `fn step(phase, reading, now) -> Phase` in `crates/core/src/commands/wait_menu.rs`. The hold comes from a core-written per-session/per-pid "last delivered action" record (core already has the session dir and every action passes `dispatch`, including raw `mouse-click`, which can record the target pid from `focused_app` or "unknown pid = global"), replacing `action_clock_store.rs`. Batch: extend `event_filter` (`src/batch/execution.rs:177`) so a following `wait --menu*` gets a pre-action reading. Unrepresentable: "closed satisfied while AwaitingOpen and before hold_until". Files: core wait.rs, new wait_menu.rs, adapter/system.rs, 3 adapters' wait.rs, linux action_clock (delete), batch execution.rs. Size M (~300). Behaviour fix for macOS/Windows can ship first by porting the Linux heuristic (S), refactor later.
- Prior art: docs/solutions doc above (Linux-only fix, from Linux PR #291 "feat(linux): wait on AT-SPI signals, menus and stopped apps"). No issue/PR for macOS/Windows. Related class: issue #433 (`wait --event window-opened` after the action times out: baseline taken after the action). Searches: listed at top (menu-closed, "wait --menu", "menu closed wait", "action clock").
- Overlap: none in upstream register. Perf change would touch `menu_wait.rs`, `windows/system/wait.rs`, `macos/system/wait.rs`.

### SURFACE-2: Notification wait baseline is captured after the action and never decreases (upstream #19, confirmed)

- Pieces: `crates/core/src/commands/wait_notification.rs:35` (`baseline: Option<HashMap<Fingerprint, usize>>`), `:46-48` (set once from the first successful list), `:49-58` (match), `:87-131` (`NotificationFingerprint` includes `actions`, `first_new_notification` compares running count with baseline count). Per-poll list goes through `notification_policy::list_with_foreground_lease` (`notification_policy.rs:20-30`), which takes the interaction lease and lets the adapter open the notification surface each poll. No pre-action baseline: batch only seeds `wait --event` (`src/batch/execution.rs:177-185`).
- States today: `NoBaseline --first Ok list--> Baseline(counts, frozen) --any count > frozen--> Matched`.
- Illegal / unhandled transitions
  1. **Frozen counts (#19).** Baseline {A:1}; A is dismissed/expires; an identical A arrives → current {A:1}, `1 > 1` false → TIMEOUT. CONFIRMED (traced `:49-50`, `:117-131`). Test sketch (FAILS on main): `wait_tests.rs` `FlakyNotificationAdapter::with_responses(vec![Ok(vec![n("A")]), Ok(vec![]), Ok(vec![n("A")])])`, call `wait_notification::wait_for_notification(None, None, 500, &adapter, &ctx)`, assert `matched == true`; main returns `TIMEOUT`.
  2. **Arrival before the baseline is absorbed.** `click Send` then `wait --notification --app Mail` (two calls): the baseline is the first list *after* the wait started. On macOS headed each list opens Notification Center (`osascript` + 500 ms sleep, `crates/macos/src/notifications/nc_session.rs:294`), so a notification that lands in the first ~1 s after the action is in the baseline and the wait times out. CONFIRMED by code; window size SUSPECTED (needs probe). Same class as issue #433 for events.
  3. **Mutable field in the fingerprint.** `actions` is part of `NotificationFingerprint` (`:91,100`). If an entry's action list changes while waiting (laid out on expand/hover), the *old* notification is reported as the new one. SUSPECTED (needs probe of whether any platform's action list changes for the same entry; Linux reads unplaced actions too, macOS reads `action_button` children).
- Hidden cost (estimate): macOS headed wait: every poll opens and closes Notification Center (osascript spawn ~100-300 ms + 500 ms + Escape + 300 ms ≈ 1-1.3 s/poll), reactivates the previous app each time and holds the global interaction lease during each poll. A 10 s wait ≈ 8 NC flashes. Windows opens/closes Action Center per poll similarly (cost unmeasured).
- Impact: **B** (timeout instead of match, or a false match).
- Proposed explicit form: `NotificationWaitState { floor: HashMap<Fingerprint, usize> }` with `fn observe(&mut self, current) -> Option<&Info>`: match when `count > floor`, then `floor = min(floor, current)` per key (decays when entries leave). Fingerprint = the single identity type from SURFACE-3 (no `actions`). Optional pre-action seed via batch (`event_filter` → also `wait --notification`) and `--wait-for`. Files: wait_notification.rs (+ new state file), batch execution.rs. Size S (<100) for the decay + fingerprint; S more for the batch seed. Pure behaviour fix.
- Prior art: upstream register #19 ("Open (likely)"). Issue #433 is the same class for event waits. No PR. Searches: "notification wait baseline", "wait --notification", "notification"; `git log upstream/main -S first_new_notification` → only #54/#311 (introduction).
- Overlap: upstream #19. Perf change would touch notification_policy.rs and each adapter's notification session (one session per wait instead of per poll).

(Needs the identity to carry body or an opaque token.)

- Impact: **A** (action delivered to the wrong notification).
- Proposed explicit form: one `NotificationKey { app, title, body_hash }` in core (`notifications/notification_key.rs`) emitted by `list-notifications` as an opaque `key` (like a ref token) and required by dismiss/action (`--key`), replacing `--expected-app/--expected-title` (keep them as deprecated filters). `NotificationKey::matches` is the only equality used by core waits and by every adapter's verify step; twins are resolved by count, never by "first".
