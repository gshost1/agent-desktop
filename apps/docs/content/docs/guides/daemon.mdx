title: Daemon mode
navTitle: Daemon mode
description: Run commands through a warm background process to skip per-call setup. Opt in with a variable or a flag; output and exit codes stay the same.
---

Every CLI call normally starts a fresh process, which connects to the platform's accessibility services before it runs the command. Daemon mode keeps one background process of the same binary running and hands each call to it, so connections that process already opened are reused. The CLI still starts per call, but as a thin client.

## Turn it on

```bash
export AGENT_DESKTOP_DAEMON=1         # every call in this shell
agent-desktop list-apps
agent-desktop --daemon list-apps      # or one call
```

The first call finds no daemon, starts one in the background, waits up to 1.5 seconds for it to listen and runs its command there. Later calls go straight to it. Unset the variable to go back to one process per call. Daemon mode is off by default.

Each command prints the same stdout and stderr and exits with the same code as without daemon mode. Nothing in the envelope says which process ran it.

## Which daemon serves a call

One daemon serves one combination of:

- user,
- binary build (version and executable file, so an upgraded or rebuilt binary gets a new daemon),
- `--session` and `--agent-id` values,
- environment: display and bus variables (`DISPLAY`, `WAYLAND_DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `AT_SPI_BUS_ADDRESS`, `XDG_*`), every `AGENT_DESKTOP_*` setting, `HOME`, `PATH`, locale and temp-directory variables.

A call with any other combination gets its own daemon. The daemon runs each command in the caller's working directory, so relative paths such as `screenshot shot.png` land where they would without daemon mode.

## When the CLI runs the command itself

The CLI runs a command in its own process, exactly as without daemon mode, when:

- the daemon could not be started or did not listen within 1.5 seconds,
- the state root does not exist yet: daemon mode never creates it, so a call that creates nothing without daemon mode creates nothing with it,
- the socket path, `<state root>/daemon/<key>.sock`, would be longer than 100 bytes; keep `AGENT_DESKTOP_HOME` short,
- the daemon is busy with another call: calls never queue behind each other,
- the daemon does not answer within 2 seconds (it is stopped or hung),
- the command reads stdin (`--stdin`), is `launch` or a `batch` that launches (the app must inherit the caller's environment), uses `--verbose`, prints help, or has an argument error,
- the call holds an interaction lease handed down by `agent-desktop mcp`,
- a permission check refused the command before it did anything (on macOS a daemon may lack a grant the caller's terminal has),
- the daemon stopped before it started the command.

## Failures

While a command runs, the daemon tells the CLI every half second that it is alive. Five seconds without that, or a closed connection, counts as the daemon stopping. If the daemon stops while it runs a command that only reads (`snapshot`, `find`, `wait`, `list-apps`, ...), the CLI runs the command again itself. A command that can change something (`click`, `type`, `session start`, ...) is never run twice. The CLI returns `INTERNAL` with `disposition.delivery: "delivery_uncertain"` and `retry: "unsafe"`:

```json
{ "version": "2.7", "ok": false, "command": "click",
  "error": { "code": "INTERNAL",
             "message": "The agent-desktop daemon stopped while it was running this command",
             "suggestion": "The command may have taken effect. Take a fresh snapshot to check before you retry it.",
             "disposition": { "delivery": "delivery_uncertain", "retry": "unsafe" } } }
```

Killing the CLI while its command runs stops the daemon too, as it would stop a one-shot process. The next call starts a new daemon. The CLI writes the command's stderr before its stdout, so when both go to one file the two streams are not interleaved as they would be without daemon mode. Refs live on disk under the state root, so refs taken before a restart keep resolving, or fail with `STALE_REF`, exactly as without daemon mode.

## Idle exit and stopping

A daemon exits after 5 minutes without a call. `AGENT_DESKTOP_DAEMON_IDLE_MS` sets the wait in milliseconds (100 to 86400000).

Each daemon keeps three files in `<state root>/daemon/`: `<key>.sock`, `<key>.lock` and `<key>.state`, which holds its `pid` and how many commands it `served`. A daemon that exits idle or is stopped with `SIGTERM`, `SIGINT` or `SIGHUP` removes its socket and state file; after `SIGKILL` the next daemon for that key replaces the socket. To stop every daemon of a state root now:

```bash
for f in ~/.agent-desktop/daemon/*.state; do kill "$(sed -E 's/.*"pid":([0-9]+).*/\1/' "$f")"; done
```

## Security

The daemon directory is created `0700` and the socket `0600`. A client uses the directory only while it is a real directory owned by its user with no group or other access. There is no network listener. A daemon serves only clients of its own user: on Linux it checks the peer's credentials and that the peer runs the same executable file, on macOS it checks the peer's user id. It refuses a client whose build or environment differs from its own.

On macOS, Accessibility and Screen Recording grants follow the app that started the daemon, usually your terminal. A daemon started from a terminal with the grants serves other callers of the same user and environment. If that matters, leave daemon mode off.

## MCP

`agent-desktop mcp --daemon` forwards `--daemon` to every tool call. A call that holds an interaction lease handed down by the server's parent always runs in its own process.

## Platforms

Linux and macOS. On Windows `AGENT_DESKTOP_DAEMON` and `--daemon` are accepted and ignored: every call runs in its own process.

Trace segments (`<pid>-<start>.jsonl`) carry the daemon's pid for the calls it ran.
